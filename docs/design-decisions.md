# 企画段階

## 1. 通知には LINE を使う

- 日付：2026-10-09（企画時） ／ 関連：#5、#9
- **決めたこと**：毎朝のアドバイスは LINE で届ける。ログインも LINE ログインにする
- **理由**
  - LINE は日本で最もよく使われているメッセンジャーアプリで、毎日開く人が多い
  - 新しいアプリを入れてもらわなくても、普段見ている場所にアドバイスが届く
  - LINE ログインにすれば、通知先のユーザーとログインユーザーを同じ ID で結びつけられる


## 2. AI は Gemini API を使う

- 日付：2026-10-09（企画時） ／ 関連：#7
- **決めたこと**：一言アドバイスの生成には Gemini API を使う
- **理由**
  - ChatGPT や Claude は普段からよく使っているので、まだ使ったことのない AI の API に触れてみたかった
- **補足**：Google AI Studio で APIキーをすぐに発行でき、クレジットカードなしの無料枠で始められる


## 3. 通知は毎朝7時に固定する

- 日付：2026-10-09（企画時） ／ 関連：#10
- **決めたこと**：通知時刻はユーザーごとに選べるようにせず、毎朝7時に固定する
- **理由**
  - まずは動くものを早く完成させることを優先し、時刻設定の画面とユーザーごとの実行管理を省いた
  - 7時は多くの人が起きて身支度を始める時間で、その日の服を決めるタイミングに合うと考えた
- **今後**：ユーザーごとに通知時刻を選べるようにする


## 4. 通知する地点は1つ（自宅）にする

- 日付：2026-10-09（企画時） ／ 関連：#6
- **決めたこと**：ユーザーが登録できる地点は1つだけにする（users と locations は1対1）
- **理由**
  - 複数の地点にすると、設定画面・通知の文面・データの持ち方がすべて複雑になる
  - 旅行や出張は毎日あることではなく、職場も自宅からそれほど遠くない場合が多いので、自宅の天気で多くの日はまかなえる
  - 別の場所の天気は、トップページの地名検索で調べられる
- **今後**：外出先の地点を追加できるようにする


## 5. 服装は6段階、体質は3段階にする

- 日付：2026-10-09（企画時） ／ 関連：#3、#6
- **決めたこと**：おすすめの服装は「半袖〜厚手コート」の6段階。体質は「暑がり・ふつう・寒がり」の3段階で、判定前の気温を ±3℃ 補正する
- **理由**
  - 服装：最低でも「とても寒い・寒い・ふつう・暑い・とても暑い」くらいの区別は必要。一方で10段階などにすると隣り合う段階の差が分かりにくく、判定ルールも増える。その間の6段階にした
  - 体質：同じ気温でも感じ方は人によって違う。ふつう・暑がり・寒がりで微調整できると、自分向けのアドバイスだと感じてもらえると考えた
- **服装の境目の温度（25／20／16／12／8℃）について**：気温と服装の対応に公式の基準はないため、一般的に紹介されている目安を採用した。日本気象協会（tenki.jp）の「服装指数」も参考にしたが、風・湿度・日射も使った独自の計算で、計算方法は公開されていない


## 6. ホスティングは Render、DB は Neon を使う

- 日付：2026-10-09（企画時） ／ 関連：#1
- **決めたこと**：アプリは Render、PostgreSQL は Neon で動かす
- **理由**
  - どちらも以前使ったことがあって慣れており、環境構築に時間をかけずに済む
  - ユーザー数も DB のデータ量も小さいこのアプリの規模に合っている

# 開発段階

## 7. 本番は Render ＋ Docker、ローカルは Docker なし

- 日付：2026-10-09 ／ 関連：#1
- **決めたこと**：ローカルは Mac に入れた Ruby と PostgreSQL で直接動かす。本番の Render は、`rails new` で生成された `Dockerfile` を使ってデプロイする
- **理由**
  - ローカルはすでに Ruby 4.0.2 と PostgreSQL 17 が揃っていて、Docker なしのほうが起動もコマンドも速い
  - 本番は Docker にすると Ruby のバージョンをイメージで固定でき、起動時に `db:prepare` も自動で走る
  - Render は Starter プランにする。無料プランはアクセスがないとスリープし、毎朝7時の定期実行が動かないため
- **検討した他の案**：ローカルも Docker（環境構築の時間がかかる）、Render のネイティブ Ruby 環境（Ruby 4.0 への対応が不確かだった）


## 8. Solid Queue / Cache / Cable を Neon の1つの DB にまとめる

- 日付：2026-10-09 ／ 関連：#1
- **決めたこと**：Solid Queue・Solid Cache・Solid Cable のテーブルを、通常のマイグレーションでメインの DB に作る
- **理由**
  - Rails 8 の初期設定では、本番でそれぞれ別の DB を使う構成になっている。Neon では1つの DB で運用したい
  - 同じ DB に4つの接続設定を向ける方法もあるが、`db:prepare` で2つ目以降のスキーマが読み込まれないことがある。マイグレーションにすれば確実に作られる
- **検討した他の案**：DB を4つ用意する（管理が増える）、同じ DB に複数の接続設定を向ける（上記の理由で不確実）


## 9. 地名検索は国土地理院、天気は Open-Meteo

- 日付：2026-10-09 ／ 関連：#2
- **決めたこと**：地名から緯度・経度を調べるのは国土地理院の地名検索API、天気は Open-Meteo から取得する
- **理由**
  - Open-Meteo の地名検索では「渋谷区」「新宿区」など区の名前が見つからなかった。「区」を外して検索すると「港」「品川」が見つからず、「浦安」で鳥取県が出るなど取り違えも起きた
  - 国土地理院の地名検索APIでは、渋谷区・新宿区・世田谷区・港区・軽井沢町まで正しく見つかった。APIキーも不要
  - 天気は Open-Meteo なら、今日の予報と昨日の気温が1回のリクエストで取れる（`past_days=1`）。APIキーも不要
- **検討した他の案**
  - 気象庁の予報データ：公式のAPIではなく、地域コードへの変換が必要。気温は代表地点のみで、昨日の気温は別途アメダスから取る必要がある
  - WeatherAPI.com：昨日の気温は取れるが、予報と別のリクエストになる。APIキーの管理が増え、日本語の地名検索の精度も不明
  - Google のジオコーディング：精度は高いが、キーとクレジットカードの登録が必要
- **注意点**：国土地理院の地名検索APIは地理院地図で使われているもので、公式に動作が保証された公開APIではない


## 10. 服装とマークはルールで判定し、AI は一言だけ

- 日付：2026-10-09 ／ 関連：#3、#7
- **決めたこと**：おすすめの服装（6段階）と傘・暑さ注意のマークは、気温と降水確率からルールで決める。AI（Gemini）には判定結果をもとにした一言コメントだけを作らせる
- **理由**
  - 服装の判定は毎回同じ結果になってほしく、テストで確かめられる形にしたい
  - AI が失敗しても、天気と服装のアドバイスは必ず出せる
  - AI の利用回数とコストを抑えられる


## 11. AI の一言はログインユーザーだけに出す

- 日付：2026-10-09 ／ 関連：#4、#7
- **決めたこと**：トップページ（ログイン不要）では AI の一言を出さず、「LINE で登録すると AI の一言アドバイスも毎朝届きます」と案内する
- **理由**
  - ログインしなくても誰でも検索できるページで AI を呼ぶと、連続で検索されたときに無料枠の回数制限にすぐ達してしまう
  - 「登録すると AI の一言が見られる」ことが、LINE ログインする動機になる
- **検討した他の案**：検索した地点にも AI を出す（地名＋日付でキャッシュすれば回数は抑えられるが、MVP では見送り）、初期表示の渋谷区だけ AI を出す（キャッシュの仕組みが必要で、上の動機づけとも合わない）


## 12. LINE の友だち状態は API で確認せず、案内リンクにする

- 日付：2026-10-09 ／ 関連：#6、#8
- **決めたこと**：公式アカウントを友だち追加しているかを API で確認せず、「通知が届かない場合は友だち追加を確認してね」という案内と友だち追加リンクを置く
- **理由**
  - 期限内に MVP を完成させるため、範囲を絞った
  - 確認しなくても困るのは「ブロックされているのに画面上はお届け中に見える」くらいで、MVP では影響が小さい
- **今後**：必要になったら、LINE ログインの friendship status API か、Webhook の follow / unfollow イベントで対応する


## 13. 気温ゲージの代わりに「昨日より○℃」の帯を出す

- 日付：2026-10-09 ／ 関連：#2、#4、#8
- **決めたこと**：寒い〜暑いのゲージをやめて、「昨日より 3℃ 低い　昨日の最高 25℃」の帯を表示する
- **理由**
  - ゲージは服装名や気温の数字と内容が重なり、ひと目で意味が伝わりにくかった
  - 「昨日より寒いか暖かいか」のほうが、服を選ぶときの実感に近い
  - Open-Meteo の同じリクエストで昨日の気温も取れるので、追加の API 呼び出しがいらない
- **検討した他の案**：いまの気温を表示する（服装は最高気温で判定するので、朝の気温を出すと誤解を招く。見送り）


## 14. 傘は「1日の降水確率の最大値が50%以上」で判定する

- 日付：2026-10-09 ／ 関連：#3、#4
- **決めたこと**：Open-Meteo の `precipitation_probability_max`（その日の降水確率の最大値）が50%以上なら、傘マークと「雨の可能性あり。傘を持っていこう」を出す
- **理由**：1日分の予報だけで判定できて、作りがシンプル
- **既知の弱点**：夜遅くだけ雨が降りそうな日でも傘マークが出る
- **今後**：余裕があれば、1時間ごとの予報で外出する時間帯（6時〜21時）だけを見る。「午後は雨の可能性あり」のように時間帯も出せる


## 15. テストは RSpec ＋ webmock

- 日付：2026-10-09 ／ 関連：#1、#2
- **決めたこと**：テストは Minitest ではなく RSpec で書く。外部 API を呼ぶ処理は webmock でリクエストをスタブ（偽物の応答に差し替え）してテストする
- **理由**
  - 前に作ったアプリは Minitest だったので、今回は RSpec を使いたかった。
  - 天気は毎日変わるため、本物の API を叩くと結果が決まらずテストが書けない。
  - タイムアウトや HTTP エラーをわざと起こして、失敗したときの動きを確かめるため。

## 16. 地名は検索して候補から選んでもらう

- 日付：2026-10-09 ／ 関連：#2、#4、#6
- **決めたこと**：地名検索の結果を1件に決めつけず、候補（最大10件）を検索欄の下に出して選んでもらう。候補が1件でもリストに出す。Yahoo!天気の地点検索と同じ考え方
- **作り方**：検索したときは Turbo Frame で候補リストの部分だけを差し替え（ページは切り替わらない）、候補を選んだらページごと切り替える（URL に地名・緯度・経度が入るので、戻るボタンや URL の共有がそのまま使える）
- **理由**
  - 1件目をそのまま使うと、「渋谷」で福島県猪苗代町渋谷、「中央区」で北海道札幌市中央区が選ばれるなど、気づかないうちに違う場所の天気を出してしまう
  - 同じ名前の地名は多い（港区は東京・名古屋・大阪にある）
  - 候補は「東京都〜」のように都道府県から始まる住所だけにし、川・山・建物は除く
- **検討した他の案**
  - 別ページに候補の一覧を出す：検索欄の下に出すほうが、どこを選んでいるか分かりやすい
  - 検索のたびにページ全体を読み直す：作りは一番シンプルだが、検索するたびに表示中の場所の天気も取り直すことになり、URL も検索のたびに変わる
  - 候補の選択も Turbo Frame で天気カードだけ差し替える：URL が変わらず、選んだ場所の天気を共有できない
  - 入力の正規化（「東京 中央区」→「東京都中央区」）：スペースや「都・府・県」の省略に対応できるが、MVP では検索欄の例（「東京都中央区」）で書き方を伝えるだけにした
  - 入力中に候補を出すオートコンプリート：JavaScript の自作と、文字を打つたびの API 呼び出しが必要。MVP では見送り
- **既知の弱点**：ひらがな（「しぶや」など）では住所が見つからない

## 17. 暑さのマークは気象庁の定義（真夏日・猛暑日・酷暑日）に合わせる

- 日付：2026-10-10 ／ 関連：#3
- **決めたこと**：実際の最高気温が30℃以上なら真夏日、35℃以上なら猛暑日、40℃以上なら酷暑日のマークを付ける
- **理由**
  - 最近の日本の夏は30℃以上が当たり前になっていて、「暑さ注意」の1段階だけでは足りない
  - 気象庁の予報用語に合わせれば、基準に根拠があり、天気予報で聞く言葉とも一致する（酷暑日は2026年に気象庁が正式に命名）
  - 熱中症の危険は実際の気温で決まるので、体質による補正はしない
- **検討した他の案**：30℃以上の「暑さ注意」だけ（当初の案。35℃・40℃の日を区別できない）

## 18. 傘は目立つ帯、暑さと寒暖差は小さなバッジで出す

- 日付：2026-10-10 ／ 関連：#3、#4
- **決めたこと**：傘が必要な日は、画面イメージどおり目立つ帯で出す。真夏日・猛暑日・酷暑日と寒暖差は、服装の近くに小さなバッジで出す
- **理由**
  - 傘は忘れると困るので、いちばん目に入るようにしたい
  - 暑さや寒暖差は「あれば気づける」くらいで十分。マークが多すぎると、大事な傘の情報が埋もれる
  - バッジは文字と背景色だけなので、画像を用意しなくてよい
- **寒暖差の基準**：最高気温と最低気温の差が7℃以上。寒暖差疲労の症状が出やすいとされる目安を採用した（公式の基準ではない）
- **検討した他の案**：前日との気温差7℃以上でも注意を出す（「昨日より○℃」の帯で伝わるので見送り）

## 19. 服装やマークの判定は、画面に出す四捨五入した気温で行う

- 日付：2026-10-10 ／ 関連：#4
- **決めたこと**：画面には最高・最低気温を四捨五入した整数で出し、服装・暑さ・寒暖差の判定も同じ四捨五入した値で行う
- **理由**
  - 判定だけ実際の値（24.6℃）を使うと、画面は「25℃」なのに服装は「長袖1枚」になるなど、表示とつじつまが合わなくなった
  - 普段見る天気予報と同じ整数のほうが分かりやすい
- **既知の弱点**：気象庁の真夏日などは 0.1℃ 単位の観測値で決まるので、29.5〜29.9℃ の日は「アプリでは真夏日、ニュースでは真夏日ではない」とずれることがある。ただ、朝の時点の予報にはそれ以上の誤差があるので、影響は小さいと判断した

## 20. 傘の文言は1種類にする

- 日付：2026-10-10 ／ 関連：#4
- **決めたこと**：降水確率50%以上なら「雨の可能性あり。傘を持っていこう」の1種類だけを出す。折りたたみ傘か普通の傘かは言わない
- **理由**
  - 本来は「出かけるときは降っていないけど降るかも → 折りたたみ傘」「明らかに降る → 普通の傘」と分けたいが、正確に分けるには1時間ごとの予報で朝の雨を見る必要がある
  - 降水確率で2段階に分ける方法もあるが、確率は「降るかどうか」で「いつ・どれくらい降るか」は分からないので、外れることがある
  - 降水確率の数字はすぐ上に出ているので、どちらの傘にするかは使う人が決められる
- **今後**：1時間ごとの予報で、朝の時間帯に降っているかどうかで傘の種類を出し分ける

## 21. AI の一言はホーム用と LINE 用を1回の呼び出しで作る

- 日付：2026-10-10 ／ 関連：#7、#8、#9
- **決めたこと**
  - Gemini に1回だけ頼み、ホーム用（短く分かりやすい）と LINE 用（砕けた、寄り添う口調）の2つの文を作って、daily_advices の `comment` と `line_comment` に保存する
  - ログイン後のホームでは、服装ごとの決まった説明文の代わりに AI の一言を出す。AI の作成に失敗した日は、決まった説明文を代わりに出す
- **理由**
  - LINE は友だちから届くメッセージのように読むので、砕けた口調のほうが合う。アプリの画面は、さっと読める短い文のほうが合う
  - 2回呼ぶより、回数制限と待ち時間に優しい
  - AI の一言と決まった説明文を両方出すと、同じような内容が2回並ぶ

## 22. LINE ログインは gem を使わずに実装する

- 日付：2026-10-10 ／ 関連：#5
- **決めたこと**：omniauth などの gem を使わず、LINE ログイン（OAuth 2.0）の流れを自分で書く（`Line::Login`、`SessionsController`）
- **理由**
  - 流れは「ログイン画面へ送る → 戻ってきた code をトークンに交換 → ID トークンを LINE に検証してもらう」だけで、自分で書いても短い
  - LINE ログイン用の gem は更新が止まっているものが多く、Rails 8・Ruby 4.0 で動くか不安がある
  - 天気の API と同じく自分で API を呼ぶ形なので、仕組みを説明できる
- **安全のためにやっていること**
  - `state`（ランダムな合言葉）をセッションに覚えておき、戻ってきたときに一致を確かめる（CSRF 対策）
  - ログインの前後で `reset_session` してセッションを作り直す（セッション固定攻撃の対策）
  - チャネルシークレットは credentials に暗号化して保存する
- **その他**：ログイン時に `bot_prompt=aggressive` で公式アカウントの友だち追加を出す。そのために、LINE ログインチャネルと Messaging API チャネルを同じプロバイダーで作って紐づけた

## 23. ログイン中の表示は LINE のアイコンだけにする

- 日付：2026-10-10 ／ 関連：#5、#6、#8
- **決めたこと**：ログイン中は、タイトルの下の行の右寄せに LINE のプロフィール画像を丸く出す。アイコンを設定していない人には人の形の線画を出す
- **理由**
  - 「○○さん、ログイン中です」の文や名前だけの表示は、見た目がしっくりこなかった
  - LINE で見慣れた自分のアイコンなので、ひと目でログイン中だと分かる
  - 画像そのものは保存せず URL だけを保存するので、画像を置くクラウドのストレージがいらない
- **既知の弱点**：LINE でアイコンを変えると、次にログインするまで古い URL のままで、画像が表示されないことがある
- **今後**：ログアウトは設定画面に移し（#6）、アイコンを押すとホームへ移動する（#8）

## 24. 画面での呼び方は「マイエリア」「体感タイプ」にする
